# Performance audit, November 2026

A whole-app pass after the last features landed (issue #494). Players mostly use the app on phones, so every finding is judged at phone speed against the budgets in [design-system.md](../design-system.md#performance-budgets). No budget was raised.

**How it was measured.** Public pages: the Lighthouse reports from CI on `main` at `1ac54974` (five runs per page on the pinned phone profile, medians below). First-load JavaScript: `npm run check:route-js` in the same CI run, which builds once and checks every route. Database reads: by reading each busy screen's code, and with the new `queriesSent` counter in the database tests, which counts the statements a query sends. Signed-in screens have no Lighthouse run, so their cost is counted in round trips: in production every query is its own HTTPS request to Neon (`src/db/client.ts`), so reads that wait for each other add up one after another.

## What checked out

- **Every public page is in the Lighthouse run.** All 36 public pages, and the embedded schedule, are listed in `lighthouserc.json`. The one left out, `/unsubscribe/[token]`, is a personal link, rendered per request on purpose and never indexed.
- **Public pages are static.** None reads cookies, headers or the query string. `/sign-in` reads its `?next=` behind a Suspense boundary whose fallback is the same form. The game page reads the clock only for its status line, forecast and photo prompt, which stream in (finding 5).
- **Every public page is inside every budget.** Performance score 99 or 100, largest contentful paint 908 to 1,073 ms (budget 2,000), layout shift 0 everywhere but the park page (0.002; budget 0.05), total blocking time 27 to 147 ms (budget 150).
- **JavaScript.** The framework's shared code is 137.5 kB. The largest route of our own is the live scoring screen at 8.6 kB (budget 45). No signed-in screen is above 5.7 kB of its own (budgets 75 and 95). Lighthouse measured 149 to 160 kB in total per public page (budget 165).
- **Fonts and images.** 90 kB of fonts (budget 120). Public images (photos, friends' logos, merch) carry their size or sit in a fixed-ratio box.
- **Cache tags.** The features of the last two days expire their pages: rules changes (`refreshRulesPage`), game-day statuses (`refreshSeasonPages`), permit windows (`refreshParkPages`), season cards (`refreshSeasonCards`) and events (`refreshEventPages`).
- **Game day.** The command center's poll is two reads (architecture.md, section 3). The score page already read its state, referee, league and live innings together; it now also reads the pickups and the captain's rating together.

## The blocking-time floor (#539)

`/faq` is the honest gauge of the framework's start-up cost: its blocking time is that one task with nothing hiding half of it. On `main`'s runs the median ranged from 73 ms on a fast runner to 151 ms on a slow one (benchmark index about 2,400 against about 3,450), because Lighthouse multiplies what the runner observed by a fixed 4x. What we own on the page is 1.0 kB of its 138.5 kB of first-load script, and measuring changes to the layout (the demo banner, 0.8 kB) and to the framework's configuration (partial prefetching, no change) found nothing to cut.

So the measurement is calibrated instead of the page changed ([ADR 0079](../adr/0079-calibrated-cpu-throttle.md)): each Lighthouse shard measures its runner's benchmark index, sets the CPU slowdown to the index divided by 862.5 (4x on a runner at 3,450, held to 2x to 6x), and logs both. The budgets, the assertions, the pages and the five runs are untouched. A `/faq` failure now means the page is slower than the phone the budget describes, not that the runner was slow; any change that adds script to the shared layout is a regression to fix in its own pull request.

## Final sweep on `main`, 16 November

A production build of `main` after the feature merges (one build; `npm run check:route-js` after it):

- Every route is inside its budget (188 routes). The framework's shared code and the site's own layout code come to 138.5 kB first-load JavaScript on most pages; the largest own-code route is still the live scoring screen at 8.6 kB (146.1 kB in total, budget 185 and 45); the largest public page is the game page at 4.7 kB of its own (142.1 kB, budget 165 and 25).
- The list in `lighthouserc.json` still covers every public page: the 38 addresses match the public page files under `src/app` (the league-scoped `/l/[league]/...` tree is the same pages behind the rewrite). Nothing was missing, so nothing was added.
- The language fonts and the pages of the language stack (#447, #448, #526, #533) are not on `main` yet, so they are not measured here.

## Keeping it this way

- A screen's reads should not grow with its rows. `inRolledBackDb` now passes each database test a `queriesSent` counter; `subs.db.test.ts` holds the sub page to the same count for three requests as for one. Add the same check when a screen lists rows that each need data of their own.
- Start reads that don't depend on each other together (`Promise.all`) and decide permissions before reading, so a screen's round trips are its longest chain of dependent reads, not its number of reads.
- The app's league comes from the data cache (#498), so a screen that reads it after the session no longer waits on the database for it.
