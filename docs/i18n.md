# Languages

How the site speaks more than one language, and how to add words, pages and languages. The decision and its trade-offs are in [ADR 0094](adr/0094-languages-from-the-path-and-the-profile.md).

## Where the words live

- `src/i18n/messages/en.ts`: every message in English. Add a message here first.
- `src/i18n/messages/<code>.ts`, with `pages.<code>.ts` and `email.<code>.ts`: the same keys in each other language.
- `src/i18n/messages.ts`: `messagesFor(locale)` returns a language's messages with any gap filled from English.

The switcher in the footer names each language in itself. Chinese is Simplified; its address keeps the short code, and the page's `lang` and `hreflang` say `zh-Hans`. Arabic needs right-to-left layout and is a separate, later change.

A page reads its language from its route (`localeOf((await params).lang)`), takes `messagesFor(locale)`, and renders the text on the server. Client components get their words as props. The browser never downloads a catalog.

- A message with slots: `fill(m.profile.language.saved, { language })`.
- A message that depends on a count: `plural(locale, m.formats.teams, n)`. Write the `one` and `other` forms, plus any other form the language's rules use. The catalog test lists them.
- Dates, times, numbers, money and lists: `src/i18n/format.ts` (`formatInstant`, `formatDay`, `formatNumber`, `formatMoney`, `formatList`). Times are always in the league's time zone.

## Emails and push

Emails to players, captains and refs, and the push notifications made from them, are written in the recipient's language: the outbox reads it from their profile as each message is sent (`src/db/queries/outbox.ts`), and the renderer passes it to the template (`src/emails/templates.ts`). Their words are in `src/i18n/messages/email.en.ts` and each language's `email.<code>.ts`. The footer, the unsubscribe line and the push notification's "Because …" line follow the language too, and a link to a translated public page goes to its address in that language.

- Emails only league admins and owners get stay in English, like the admin screens: they are listed in `ENGLISH_ONLY_TEMPLATES`.
- Emails added after the Spanish ones were written (acting admins, captain polls, game rulings, incident reports, interest go-aheads, leadership check-ins, lost and found, start-on-time and team changes) are listed in `NOT_YET_TRANSLATED` and come in English, frame and all, until they are translated.
- What the league wrote into a message when it was queued, such as a game's teams, day and time, a deal, an announcement or a win-back email, is shown as written. Days and times inside an email are written when the message is queued, in English; the gear reminder, which stores the game's start, writes them in the recipient's language.
- No language on the profile, or no account: English.

## Client components

A client component never imports a catalog. Its words come as props from the server page, which reads `messagesFor(locale)`. When it needs an English default, its words live in their own small module that the catalog spreads in, such as `live.en.ts` (the live line score) and `share.en.ts` (the share buttons).

## Checks

`npm test` runs `src/i18n/catalogs.test.ts`, and CI runs it on every pull request. It fails when a catalog:

- is missing an English key, or has a key English doesn't;
- changes a message's `{slots}` or turns a plural into a plain message;
- leaves out a plural form the language needs (Russian and Polish must write `many` too, which covers "5 команд");
- or leaves a message blank.

So a message added in English fails the build until it is translated, and the failure lists the keys.

## Serving a page in another language

A public page is served at `/es/...` only once it is on the `TRANSLATED_PAGES` list in `src/i18n/pages.ts`. Until then, `/es/...` goes to the English page. Only listed pages get `hreflang` alternates and a sitemap entry in the language. The footer's language links go through `/language/<code>` (`src/app/language/[locale]/route.ts`), which sends the visitor back to the page they were on, in that language where it is translated and to that language's home page where it isn't. They show once a second language has a translated page, and they ship no client JavaScript. To translate a page:

1. Move all of its words into the catalogs and read them with `messagesFor`. A shared helper or component takes an optional `locale` (English by default), so its other callers don't change. `domain/` may import `i18n/`; both stay free of framework and database code (the lint rules check).
2. Format its dates, times, numbers and money with `src/i18n/format.ts`.
3. Give it `hreflang` alternates with `languageAlternates(path)`.
4. Add its path pattern to `TRANSLATED_PAGES`.
5. If it's a public page Lighthouse checks, add its `/es` address to `lighthouserc.json`.

Signed-in screens follow the person's own language setting (on their profile) once `SIGNED_IN_LOCALES` includes it. Emails and push already use that setting (see Emails and push above).

A help role is served in a language once it is in `TRANSLATED_HELP_ROLES` (`src/app/[lang]/help/articles.ts`) and its pages are in `TRANSLATED_PAGES`. Its articles live in their own file, such as `articles.es.ts`, with the same ids and steps as the English ones; a test checks that they match.

## Text the league writes

The waiver and the rules are written by admins, in the league's language, and shown as written. A translation an admin adds is shown beside it, marked as a translation. The waiver is never machine-translated, and a translated waiver is never the binding text.

## Fonts

The site's web fonts cover Latin and Cyrillic, and the Latin files every page loads already have the Italian and French letters. Chinese, Korean and Bengali use the phone's own font for their script, named per language in `src/app/globals.css` (`--font-script`), because a web font for them would not fit the font budget. Polish pages use the phone's own font throughout: the web fonts do have Polish letters, but in Latin Extended files that would add about 105 kB to every Polish page, past the budget ([ADR 0095](adr/0095-the-phones-own-fonts-for-other-scripts.md)). Lighthouse CI checks one page in each language.

## No paid translation

The Spanish is written by hand, and the other languages are machine-drafted, all without a paid translation service or API ([ADR 0021](adr/0021-free-services-only.md)).

**Before launch, a native-speaking player should review every message in each language**: `src/i18n/messages/<code>.ts`, `pages.<code>.ts` and `email.<code>.ts`, and for Spanish the help in `src/app/[lang]/help/articles.es.ts`. Each language other than English and Spanish is **machine-drafted and needs a native speaker's review**. The review should check the tone (each language's note in the glossaries above), the game words, and that each message fits on a phone. Leave review notes in a pull request that edits only that language's catalog.

## Reporting a wrong translation

Every page in a language other than English has a link at the foot of the page, "Spot a wrong or clumsy translation? Tell the league", to the contact page. The message reaches the league's admins like any other; whoever fixes it edits that language's catalog in a pull request.

## Adding a language

1. Add its two-letter code to `LOCALES` in `src/i18n/locales.ts`, with its formatting tag in `LOCALE_TAGS`, its `lang` and `hreflang` tag in `LANG_ATTRIBUTES`, its Open Graph locale in `OPEN_GRAPH_LOCALES` and its own name in `LOCALE_NAMES`.
2. Add `src/i18n/messages/<code>.ts`, `pages.<code>.ts` and `email.<code>.ts`, and list the language in `CATALOGS`. Add a glossary above.
3. Teach `formatOrdinal` (`src/i18n/format.ts`) how the language writes "3rd" in the catalog's phrases, and check that `Intl` has formatting data for it (Haitian Creole doesn't: see ADR 0095).
4. Add a migration that widens the `profile_language_known` check (`npm run db:generate` picks it up from `LOCALES`).
